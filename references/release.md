# 验证、发布与持续维护

## 发布门禁

把结果填入[发布记录](../assets/release-record.md)。每条标为通过、失败、未执行或不适用，并关联版本与证据。不适用需理由。

1. 核心用户任务可完成，真实内容及必要帮助/联系入口就位。
2. 适用lint、类型检查、单元/集成、生产构建通过；测试关注规则、权限与错误分支，不机械堆数量。
3. 部署平台产物可构建和预览；本机Node成功不足以证明Workers成功。
4. 生产模式关键浏览器流程通过，含手机、刷新、错误/空态；检查控制台和网络。
5. 有账号时验真实用户隔离；有模型/支付/邮件时分别验真实外部服务。仅模拟通过不能放行依赖真实服务的功能。
6. 个人网站不存储重要或敏感资料。检查源码、Git 历史、下载附件、前端 bundle、source map、构建产物和日志，确认无密码、密钥、token、身份证件、财务/健康隐私及他人未授权材料；配置范围、缓存和公开/私有数据边界正确。隐藏链接、robots.txt、noindex 不作为保密措施。
7. 发布目标、版本、数据库变更、回滚方案、成本与授权范围已明确。

只有文档变化不运行应用全量测试；但第一次上线必须覆盖实际部署路径。生产环境测试用最小的受控数据，不批量删除业务数据。

发现敏感信息或凭据泄露时暂停发布，先由获授权人员撤销/轮换凭据，再评估历史、下载副本、缓存和第三方服务中的暴露范围；移除当前页面不足以证明清除所有副本。涉及真实个人信息时，按适用要求处理通知和补救。参考 [安全报告](../SECURITY.md) 与 [法律声明](../LEGAL.md)，不自动删除历史或变更账号凭据。

## CI和版本一致性

建立验证流水线：检出代码→冻结锁文件安装→适用静态检查和测试→生产构建→平台构建→关键E2E→保留日志/报告。保护生产secret，勿将其提供给不可信PR；验证任务通常不需要生产管理员凭据。

发布流水线与CI分开：使用精确不可变提交SHA或已验证产物digest；校验该版本适用CI成功；检出同一版本；注入目标环境配置；部署；输出平台version/deployment ID。若重建而不是提升同一产物，记录构建环境和配置差异并重新验收。

GitHub手动工作流须先确认入口可见和默认分支包含相应定义，使用`gh workflow list/view`或API确认实际inputs，勿照抄其他仓库的workflow ID。workflow运行的元数据head SHA未必是业务代码checkout SHA，二者分别记录并查检出日志。[GitHub官方说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

环境名字符串不自动建立GitHub Environment保护；如需审批/环境secret须在job与控制台真实配置。生产发布按目标串行，避免两个版本交错；检查secret更新是否立即影响现网，避免构建失败却已经改变生产配置。

## 路线A：Next.js＋Cloudflare Workers

1. 先阅读[Cloudflare当前Next.js指南](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/)和选定适配器文档。官方推荐可能变化；OpenNext是可选路线之一，新项目按版本兼容、稳定性及实测选择，不自动迁移老项目。
2. OpenNext路线先核对[适配器文档](https://opennext.js.org/cloudflare)：安装兼容版本、配置入口/静态资产、必要兼容标志与日期、缓存和服务bindings。Worker运行在workerd，Node兼容标志不等于完整Node环境。不要把适配器特有配置写成所有Next部署的必需项。
3. 开发、生产构建、适配器本地预览分开执行，特别检查SSR、Server Actions、鉴权cookie、图片、深链及CSP。必要的R2/KV/限流绑定明确建于哪个环境；未配置不假装可用。
4. 锁定适配器CLI后以`--help`核实build/preview/deploy/upload语义。OpenNext常用build、preview、deploy；部分项目的`npm run preview/deploy`已包含build，先读脚本避免重复。上传版本不一定切换生产流量。
5. 授权后在用户Cloudflare账号创建目标资源，按最小权限配置部署token；secret通过平台安全接口注入。先验预览，再绑定正式域名/切流量。预览不可复用生产私有数据缓存。
6. 记录SHA、部署ID、绑定配置、域名和检查结果。SSR私有页/API禁止共享CDN缓存；缓存设置按框架和数据类型核对。

## 路线B：静态托管或全栈托管

静态站明确构建目录、路由基路径、深链回退与真实404；仅确实无需SSR/API/Server Actions时才能静态导出。发布到预览URL检查后再连接正式域名。

全栈托管先核对受支持版本/运行时、构建根目录、环境变量、函数时长/区域、定时任务和计划用途限制。连接仓库前理解自动部署触发，避免一次push意外触发生产；设置预览与生产分支/环境。完成预览→生产提升→版本核验→公网验收。

## 路线C：容器/VPS

根据当前框架指南构建产物或容器；保留镜像digest或发布目录。非root进程、反向代理、TLS自动续签、进程守护/重启、健康检查、最小网络开放、日志轮转均须落地。数据库不公开裸露，凭据在运行时安全注入。

部署前上传新版本到独立目录/镜像并验健康，再切代理流量，保留旧版本。磁盘、数据库和上传文件不放易失容器层。涉及多副本时核对共享缓存、会话、Server Actions密钥等框架要求。[Next.js自托管说明](https://nextjs.org/docs/app/guides/self-hosting)

## 数据库迁移与回滚

应用发布不自动意味着数据库迁移完成。记录migration ID、目标项目、执行结果。先新增兼容结构→部署兼容代码→迁移数据并验证→后续再移除旧结构；破坏性变更需明确范围授权与恢复证据。

应用回滚通常是恢复上一个平台版本/镜像并验证关键流程，不是reset源码。数据库回滚可能丢失新写入，优先兼容修复/前向修复；未演练恢复时如实说明。回滚计划必须给出真实平台入口或经核验的命令、已知良好版本、触发条件、操作者、数据库/secret/DNS是否也需要处理。

## 公网验收

在正式URL执行未登录首访、关键深链、桌面/手机主动作、刷新恢复、404；必要时验登录/退出/重置密码、持久化、下载文件内容、真实供应商结果。确认部署的实际业务SHA，不能只看流水线绿色。

检查HTTPS、重定向、混合内容、安全头与框架交互。HTTP探活、浏览器验收、业务质量和真实用户反馈分别记录。面向地区受限或移动用户时，用真实目标网络采样，不能把测试机访问成功外推。

## 运维交接

交接资源归属与权限、构建/发布/回滚入口、配置名和安全存放位置、域名续费、证书、数据库/上传备份及恢复演练、删除/导出范围、问题反馈入口和负责人。

按项目风险配置可用性、错误率、延迟、数据库容量、AI/邮件/流量账单告警；告警须能到达负责人并测试。定义维护频率、依赖更新策略和复验路径。若用户没有授权持续监控，交付运行手册即可，不擅自创建自动任务。

交付质量以可验收的任务闭环、响应式体验、数据边界、可重现发布、故障恢复和维护能力衡量；页面数、测试数与视觉风格都不是门槛。
