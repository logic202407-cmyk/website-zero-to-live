# 个人网站快速上线

适用于求职、作品集和个人介绍。先完成一个能够展示真实材料的网站，再按需要扩展。

## 1. 整理输入与公开边界

只问尚未明确且影响制作的信息：目标岗位/读者、已有材料、允许公开的身份与联系方式、风格偏好、域名和预算。没有答案的可逆设计选择先说明假设并做预览，不用技术选型问卷阻塞用户。

从简历、文档和作品中提取事实：用户承担了什么、采取了什么动作、留下什么可验证结果。确认是否可以公开姓名、照片、学校、公司、客户材料、联系方式和数字；用户提供资料不等于同意全部上网。

存在商业保密或他人信息时，遮盖标识或改用用户有权分享的样例，并如实标为样例。保留不确定项，不编造数据、评价、奖项或AI生成的客户证明。

## 2. 默认首版

优先单页或少量静态页面：

1. 简洁介绍：身份或角色、方向、能提供什么价值。
2. 代表作品：选择已有且可公开的案例，不要求固定数量。
3. 每份作品：任务背景、本人角色、过程、实际产物、可核验结果及限制。
4. 经历/能力：只放有依据且对目标岗位有用的内容。
5. 联系入口：用户批准的邮箱、社交链接或简历下载。

技术岗位可展示实现、源码和验证；非技术岗位可展示设计、分析、策划、写作、运营过程及产物。不要把所有作品都写成代码项目，也不要强迫没有量化证据的案例报增长率。

## 3. 默认技术路线

无登录和共享数据需求时，选择维护成本低的静态实现与静态托管；小站可用HTML/CSS/少量JS，内容复杂或已有框架时按现状选择SSG/SSR。优先实际环境能构建、能验证的路线，不为了套技术栈增加数据库和模型API。

默认可以使用邮件链接联系。需要真实表单时接可靠服务并验证送达；不要做“看似成功、实际未发送”的前端假表单。

公开简历下载应生成只含批准信息的版本。检查下载文件自身、文档属性、截图和图片背景中是否包含私人信息；不默认把用户原始文件直接部署到public目录。

## 4. 制作与验收

从真实内容确定信息层级、字体、色彩和布局，避免把所有岗位套成同一模板。先把主旅程做通，再补充装饰性细节。视觉方法见 [design.md](design.md)，开发方法见 [build.md](build.md)。

最少检查：手机与桌面可读、主要导航/联系/作品链接可操作、键盘焦点可见、无破坏操作的溢出、图片/字体加载正常、深链刷新和404符合预期；有下载时核验实际文件字节与内容。

配置title、description、favicon和必要的分享预览信息。没有事实依据时不添加作品评价、获奖或业务效果的结构化数据。预览域名与正式域名的索引策略分别管理。

## 5. 预览到正式上线

尽早使用平台地址建立可审阅预览；没有自有域名也能先验证网站。需要域名时按 [domains.md](domains.md) 形成准确购买方案，再依据授权完成配置。用户追求可访问的首版时，域名购买不是本地制作和预览的前置依赖。

发布需绑定已验证版本。记录真实公开URL、HTTPS、关键操作、访问网络和限制，具体方法见 [release.md](release.md)。不要把本机开发地址、只有登录才能访问的预览或截图称为公开网站。

## 6. 面试与后续维护

用 [制作记录](../assets/build-notes.md) 说明：为什么做、哪些内容和判断来自本人、AI协助了哪些步骤、本人如何复核、真实运行结果和下一步改进。

如果网站不含模型功能，明确它是AI辅助制作的网站；不宣称具备未实现的AI推荐、自动分析或真实用户效果。代理帮助用户理解源码与维护入口，不能只交付用户完全无法解释的生成结果。

交接修改内容的位置、预览方法、重新发布入口、域名续费和恢复步骤。对用户批准的资料形成版本化修改，不将私人原稿混入后续公开提交。
