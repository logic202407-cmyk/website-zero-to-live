# 选择足够的架构

先回答五件事：内容多久变化、是否必须被搜索发现、是否有私有数据、是否有长任务/实时连接、谁负责日常维护。再核对受众地区、预算、团队熟悉度和迁移成本。

| 网站类型 | 起步路线 | 按需增加 | 首要验收 |
|---|---|---|---|
| 作品集、企业展示、活动落地页 | HTML/CSS或静态生成框架＋静态托管 | 表单服务、轻量内容编辑 | 内容可信、链接、手机阅读、表单真实送达 |
| 文档、博客、新闻或频繁编辑的内容站 | SSG/SSR＋文件内容或CMS；编辑频繁且非技术团队可选成熟CMS | 搜索、预览、角色与发布审核 | 草稿不外泄、发布与更新、重定向和SEO |
| 内部工具、可视化后台 | SPA＋API，或现有全栈框架 | 登录、权限、导入导出 | 成员/组织隔离、表格任务、错误恢复 |
| 预约、会员、SaaS业务系统 | SSR/全栈应用＋数据库＋认证 | 邮件、支付、队列、对象存储 | 并发、状态一致、持久化、访问控制 |
| 商城/订阅 | 优先评估成熟电商或支付托管能力 | 经验证的订单、库存、退款、税务集成 | 以服务器事件确认付款；验签、幂等、对账、退款 |
| AI工具 | 在普通业务网站上增加服务端模型适配层 | 队列、额度、异步结果、评估集 | 失败降级、结构校验、真实调用、成本可控 |
| 视频、协作、重计算 | 前端＋专用媒体/实时/任务基础设施 | 消息队列、转码、常驻服务 | 真实负载和连接生命周期，不硬塞短请求函数 |

这些是选型起点，不是排他的语言规定。已有 Python/Django、PHP/Laravel、Vue/Nuxt 等实现时保留合理架构，套用相同验收流程。

## 全栈业务网站参考组合

- Next.js App Router＋React＋TypeScript：页面、服务端渲染、Route Handler/Server Action。
- Tailwind＋可访问的组件原语：形成统一token与组件；不要求每项目都安装shadcn。
- Zod做边界校验；复杂表单再考虑React Hook Form；有客户端服务器缓存需求再引入TanStack Query；跨组件本地交互确有需要再引入Zustand。
- Supabase Auth/Postgres/RLS或等效后端：需要账号和共享持久化时选用。文件上传才增加对象存储。
- Vitest/Testing Library、Playwright或目标语言的等效工具；CI与部署工具分开。
- Cloudflare Workers＋合适的框架适配器是一个部署选项，Vercel、托管容器或VPS也是选项。

不要照搬案例或教程在某一天的包版本。确定 Node/框架/适配器/认证SDK兼容组合，记录官方支持依据，提交锁文件；已有项目不因新教程使用新版就整体升级。

## 托管决策

| 路线 | 适用理由 | 需要承担 |
|---|---|---|
| 静态托管/CDN | 内容为主，无请求时服务端逻辑 | 表单、认证等另接真实服务；刷新深链与404 |
| 全栈托管 | 团队希望减少基础运维 | 地区访问、套餐允许用途、账单、平台耦合 |
| Workers/边缘运行时 | 适配通过且希望结合DNS与边缘服务 | 不是完整Node服务器；API兼容、包体/CPU/任务时长、连接限制 |
| 容器/VPS | 需要常驻进程、特殊依赖或可控部署地区 | TLS、反向代理、补丁、进程守护、容量、备份、监控 |
| 托管CMS/商业建站平台 | 内容维护或标准销售比定制逻辑重要 | 套餐、数据导出、域名与账号归属、扩展限制 |

不要声称境外平台一定能在中国大陆稳定访问，也不要默认反向代理能解决。用目标地区真实网络、设备和关键流程测量；只能记录未知时就写未知。

正式推荐前检查当前价格和限制，预算包含域名续费、计算、数据库、存储/出站流量、邮件、监控、AI及付费插件。免费额度不是永久成本保证。涉及地区准入、备案、隐私、交易等要求时，根据实际经营主体、部署地区和数据处理查官方来源；不能用服务器位置一句话代替判断。

## 架构决策记录

记录选项、理由、兼容版本、当前成本来源与日期、不能满足的条件、迁移触发点，以及数据导出方式。新站先做最小运行时探针：页面＋真实服务端请求（需要时）＋生产构建；发现不兼容在大规模开发前换路线。
