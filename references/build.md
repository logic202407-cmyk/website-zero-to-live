# 从空目录到可发布功能

## 建立可重现基线

1. 确认目标目录为空或现有结构已理解。读适用规则，记录Git分支、HEAD、已有改动及命令工作目录。不要覆盖用户文件或自动切到历史分支。
2. 检查Git、目标语言运行时、包管理器和平台CLI。优先项目指定版本；依照官方文档核对系统要求和脚手架参数。
3. 空项目使用官方脚手架，或小静态站直接建立源文件。先运行脚手架的帮助，选可复现版本；不盲用过期命令或生产依赖的`latest`。
4. 创建Git仓库（尚不存在时）、合理`.gitignore`、只含占位符的`.env.example`、最简README和启动脚本。排除真实env、凭据、数据库副本、用户上传、node_modules和构建缓存。
5. 第一次安装产生锁文件；以后按所选包管理器使用冻结锁文件安装。固定CI运行时和包管理器；先本地构建，再做目标运行时构建。

Next.js示例：先从[官方安装说明](https://nextjs.org/docs/app/getting-started/installation)选择版本。下面是参数化操作，替换版本、目录后再执行；不是强制选型。

```text
npx create-next-app@<已核验版本> <新目录>
cd <新目录>
npm run dev
npm run build
```

按实际生成的`package.json`补充lint/typecheck/test脚本，先核对命令存在。生成器不保证自带所有脚本；不要使用`--if-present`掩盖缺少关键门禁。Next.js新版本可优先读安装包内的`node_modules/next/dist/docs/`。Windows执行npm脚本可用`npm.cmd`；所有命令注明cwd。

## 一个纵向切片

为一条首要旅程定义：输入、权限、业务规则、输出、存储范围、重复提交行为和失败反馈。先用代表性数据完成它，再复制成熟模式扩展。

推荐分层按复杂度采用：

```text
界面/路由 → 请求边界和身份验证 → 应用用例 → 领域规则
                                             ↓
                                  Repository接口 → 数据库/本地适配器
```

静态站不需要Repository。复杂业务中避免组件直接散落SQL、存储键和模型API调用。前端即时校验改善体验，服务端重新校验维护可信边界；客户端传来的owner、价格、角色都不能作为授权依据。

- 数据契约明确`缺失/未知/空/0`含义、版本、时间、所有权。保存与导出保留用户需要的历史；是否append-only按业务决定。
- 数据层本地替身用于开发；明确刷新、跨设备、实例重启会发生什么。生产必需持久化未接通时应明确失败，不能伪装保存成功。
- 处理重复提交、慢请求、断网、过期会话、无权限、空列表和损坏缓存。需幂等的写操作用持久化唯一键/事务，不只禁用按钮。
- 对复杂共享配置采用版本控制与增量迁移，不覆盖旧历史；接口改变时同时迁移调用者与测试。
- AI、邮件、支付等供应商走独立适配层，便于替换、模拟和区分错误；secret留在服务端。

## 环境与配置

建立变量表：名称、用途、public/secret、构建期/运行期、local/preview/production、注入位置、是否必需。表中不填真实值。

Next.js的`NEXT_PUBLIC_*`会暴露给浏览器并常在构建期内联；切换生产后端地址后仅修改运行时secret不一定有效，需要用正确公开配置重建。客户端公开key不等于管理员key。

预览与生产隔离数据库、回调URL、支付模式、邮件收件人和AI额度；不可因预览写入了生产数据库就把验证称为无副作用。

## 开发循环与协作

每轮：定义边界及验收→读取相关实现→完成小切片→运行适用检查→查看差异→记录结果→形成原子提交。只stage本轮文件；提交不自动等于push或部署授权。

若已授权多人/多代理协作：用例、数据契约、文件所有权和禁止改动范围先定清；接口变更先通知调用方；交接包括SHA、命令、结果与未验证项。检查其他参与者正在写的文件再修改，不把旧backlog当作本轮任务。

UI外观改动做截图和交互验证；逻辑改动做针对业务行为的测试；文档改动查引用与结构。避免为低影响文案变更机械跑全套E2E。
